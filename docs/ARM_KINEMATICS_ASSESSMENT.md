# 手臂运动栈评估，以及 2026-11-04 抬升与收手故障全记录

> 2026-11-05：下文保留为11/04历史记录。当前撤离实现已改为连续局部IK抬升、固定电机关节中转位及统一时间规划/反馈执行，见 [STAGED_RETRACT_V3.md](STAGED_RETRACT_V3.md)。下文临时放宽J2及准备位在线IK已移除；电机角与模型角须转换后才能比较限位，不能直接比较日志电机角与YAML限位数值。

日期：2026-11-04。对象是本机正在用的闭源 `Robot_Arm`（`include/Ti5_Arm.h`，实现在 `lib/Ti5_Arm_2204.so`）以及仓库里包在它外面的播放器、连接器和后来加上的连续抬升、关节收手。闭源库只评它公开给上层的合同和现场已经暴露的行为，不猜测 `.so` 内部还有哪些未导出函数。

这份文档分两块。前半是 SDK 和人形开源方案的对照，结论在当天上午已经成立，后面的现场没有推翻它。后半按时间记下抬升、收手一路上每次失败、每次复算、放弃过的办法，以及现在代码实际在做什么。

## 结论

七轴手臂在末端位姿定死之后还剩 1 个自由度。同一条直线、同一个准备位，可以对应很多套关节角。SDK 的笛卡尔直线会自己再选一套，不保证就是手臂现在停住的那一套。连接器发现对不上，就整段取消。模型限位表又比实机窄，单点逆解会把每天都在用的准备姿态直接判成非法。

这两件事不是一回事，后来被混在同一次“收手失败”里：

- 孔边竖直上抬必须贴着当前关节走，否则零件还在孔里会被横着拧。这里用连续积分，不用 SDK 直线。
- 抬完回传送带准备位不需要保持末端路径。这里用一次逆解加上 `Joint_Trajectory`。这次逆解单独放宽 J2，抓取仍用原限位。

回 home 几乎总能成功，是因为它把 SDK 直线直接播出去，没有连接器，也没有 2 秒到位窗。它同样会重选肘，只是没人把这判成失败。

## 当前栈里实际有什么

| 层 | 位置 | 实际在做什么 |
|---|---|---|
| 解算器 | SDK `Forward_Kinematics` / `Jacobian` / `Inverse_Kinematics` | 单臂。七轴混合解：数值法先估计 J2，再解析求精。另有指定 J2 的解析解，和带零空间的数值解。七轴返回 -3 时，头文件写的是腕部奇异或关节超限 |
| 规划器 | SDK `Line_Trajectory`、`Joint_Trajectory` | 笛卡尔直线沿路径逐点逆解，可选把 J2 从起点插到给定终点。关节轨迹是两端之间的五次多项式，不保证末端走直线。直线规划有时能给出超限模型也拒绝的单点逆解 |
| 播放器 | `execute_arm_trajectory`（`src/function.cpp`） | 5 ms 开环写电机位置。跟随误差不回灌。若伺服还在保持某一组关节，会先做连接，接不上就返回 -16，轨迹一个点都不发 |
| 伺服里的局部解 | `src/motion/pose_solver.cpp` 的 `solve_pose_with_fk` | 有限差分雅可比、阻尼最小二乘、最多 6 步、单步关节增量封顶 0.05 rad。视觉下降每拍从上一步接着算，所以下降是连续的 |
| 连接器 | `include/servo/trajectory.h` 的 `connect_held_start` | 五次 Hermite。关节差超过 0.05 rad 直接拒绝。衔接过程中末端不能再低下 2 mm，水平不能挪过 8 mm。接缝加速度上限 6 rad/s² |
| 模型限位 | `config/Robot_Arm_Model.yaml` | 右手 J2 上限 5°，左手 J2 下限 +5°。现场抓取肘可以到大约 74°，准备姿态肘在 ±45° 附近。`visual_servo.enforce_sdk_joint_limits` 为 false，只放过下降时的局部求解，SDK 内部逆解仍按这张表返回 -3 |

调用关系，改完之后：

| 动作 | 谁调用 | 抬升 | 收回准备位 |
|---|---|---|---|
| 料盘一抓取 | `run_grasp_to_standby` → `retract_staged` | `arm_vertical_lift`，连续积分 | `arm_return_after_lift`，关节插值，目标是传送带一 `conveyor.tcp` |
| 料盘二放置 | 同一个 `retract_staged`，放置标志为真 | 同上，高度用 `tray2_place.retract_lift_m` | 同上，目标换成传送带二准备位 |
| 传送带抓取 | `grasp_lift_and_back` | `arm_vertical_lift` | `arm_return_after_lift` |
| 传送带放置收手 | `lift_and_retract` | 不走上面两个函数 | 仍是 `arm_dual_line_then_line_nostop`，这次没改 |

`arm_return_after_lift` 声明在 `include/function.h`，实现在 `src/function.cpp`。料盘技能和传送带抓取都调用它，符合仓库第二步的方向：运动原语留在这一层，不要在 `grasp_to_standby.cpp` 里只改料盘抓取。

## 业内开源实际在用的做法

下面这些是人形和双臂栈里现在还在维护、并且直接解决“同一末端位姿选哪套关节”的方案。模仿学习和 VLA 不在这张表里：它们不负责孔边这 80 mm 的运动学连续性。

| 方案 | 解决的问题 | 和这次故障的关系 |
|---|---|---|
| [Pinocchio](https://github.com/stack-of-tasks/pinocchio) | 多体正解、雅可比、关节限位，人形模型的公共底层 | 本机 MDH 单臂正解能用，但腰、双臂、头不是同一个模型 |
| [Pink](https://github.com/stephane-caron/pink) | 把末端位姿和偏好关节写成加权任务，二次规划求关节速度再积分。`PostureTask` 把当前关节当作偏好构型。示例包括 Yumi 双臂、Iiwa 全身自碰撞、Draco 3 人形 | 上抬若走这条路：末端沿 +z、姿态高权重、姿态任务低权重贴着抓取构型。冗余不会另选一套肘 |
| [mink](https://github.com/kevinzakka/mink) | 同一类微分逆解，后端是 MuJoCo。G1、Apollo 示例把骨盆、躯干、双手、双脚、质心和姿态放进同一次求解，关节限位和碰撞是硬约束 | 双臂同时抬、并躲开另一只手和身体，是这一层的事。本机两只手各算各的 |
| [Shimizu 等，2008，IEEE T-RO](https://doi.org/10.1109/tro.2008.2003266) | SRS 七轴的解析解用臂型角（肩—肘—腕平面相对参考平面的转角）参数化冗余，并在关节限位下挑离当前臂型角最近的解 | 这是“人形臂姿态”的经典专用参数。SDK 锁的是 J2 电机角，几何上不等于臂型角 |
| [Ruckig](https://github.com/pantor/ruckig)、TOPP-RA | 在已经确定的路径上做在线加加速度限制或时间最优参数化 | 只安排时间，不选关节。解决不了换支，也解决不了限位把解丢掉 |

当时的判断：80 mm 上抬不需要上 Pink 或 mink。那些是腰、双臂、自碰撞以后的栈。缺的只是“从当前关节积分，不要重新选支”。臂型角解析解是七轴的正统参数，但本机左右 `model_direct` 相反，SDK 暴露的冗余不是臂型角，为这一次上抬重写解析解更容易再选出另一支。Ruckig 用不上。

后来收手证明了另一件事：不需要保持末端路径的动作，连微分逆解都不该用。SDK 里已有的 `Joint_Trajectory` 就是关节空间插值，中间没有选解。真正要升级 SDK 的，仍是那些必须保持末端直线的动作：`Line_Trajectory` 应把传入的起点关节当成硬起点，并让冗余沿这一支连续走。升级之后连接器可以去掉。收手不属于这一类。

## 批判

### 落后，但不是没有

**单臂七轴逆解是上一代工业臂的做法。** 混合解先用数值法猜一个 J2，再解析求精。猜出来的 J2 只要和当前差一截，解析解就会整支跳到另一套肩、肘、腕。数值解的头文件写了“阻尼最小二乘 + 零空间”，但零空间目标不是调用参数。上层无法说“零空间请保持抓取时的肘”。能传的只有一个冗余关节的终点值。直线规划在传入该值时，只是把 J2 沿路径插值，其余六个关节仍逐点重解。现场已经证明：锁住 J2，J3 或 J5 仍会跳。

**关节空间五次多项式不管末端路径。** `Joint_Trajectory` 适合点到点。用它在孔边抬手，末端会走出弧线，零件会被横拖。用它在已经抬离之后回准备位，则正合适，因为这段不要求末端走直线。

**播放器是开环位置流。** 5 ms 把表里的角度写成电机位置，不看跟随误差，也不在播放中改表。SDK 直线末尾自己会减速，指令结束时手臂通常已经在目标旁边。自己采样的连续积分如果一直巡航到最后一拍，指令结束时手臂还可以落后几十毫米，随后的短等待就会被判超时。

**连接器是补丁，而且补在错误的一层。** 五次 Hermite 只能在两套已经很接近的关节之间做短过渡。0.05 rad 的门槛和“不许下压、不许横移”在孔边是对的。它失败就取消动作，说明规划器把选解问题扔了出来。把门槛放宽只会让腕在孔里横着挪。连接器也解释不了“逆解返回 -3”：那时候轨迹还没生成。

**模型限位和实机不一致，而且各接口执法不一样。** 同一张 yaml，`Inverse_Kinematics*` 会因超限返回 -3；`Line_Trajectory` 却能对同一个准备位给出整条轨迹。伺服又用另一个开关把下降时的限位检查关掉。所以上层会看到“这个点明明能走到，逆解却说没有”。

**仓库里的局部解算本来只活在视觉下降里。** `solve_pose_with_fk` 一次吃不下 80 mm：6 次迭代、每步最多 0.05 rad，一共大约 0.3 rad，而 80 mm 上抬的近端关节常常要 0.3 到 0.5 rad。所以连续抬升必须拆成大约 10 mm 一段，每段以上一步关节为种子。这是步长，不是另一套检查。

### 完全没有

- **臂型角。** 没有肩—肘—腕平面这个冗余参数，也就不能在解析的多组解里选离当前臂型最近的一组。
- **姿态任务。** 没有“末端任务优先，其余关节靠近当前角度”的二次目标。这是 Pink、mink 解决人形冗余的那一项。
- **带硬限位的微分逆解。** SDK 是解完再按模型限位丢掉，不是在真实行程内走能走的那一段。
- **双臂和全身。** 左右手是两个 `Robot_Arm`。腰是另一套五轴。没有共同的任务，没有两手之间的碰撞，没有手和躯干的碰撞。
- **自碰撞和工件碰撞。** 孔边的“不许横移”是连接器上的两个常数，不是几何模型。
- **在线时间参数化。** 没有 Ruckig 或 TOPP。速度是规划前写进 `Cart_Linear_Velocity` 的一个数。
- **播放闭环。** 没有按反馈重定时。表播完再另开一段等到位，等到位的门限和回 home 不是同一套。

## 第一场故障：上抬被连接器取消

日志：`logs/visual_servo/servo_1793769427696785_34524.csv`，约 13:17。

两只手都到了 `ready_precise`，夹爪都收到约 1.54 rad，判定夹住。然后：

| | 抓取高度 | 上抬结果 |
|---|---|---|
| 右手，y ≈ -0.028 | 约 4.7 mm | 两次规划都是 -16，手臂没动 |
| 左手，y ≈ 0.177 | 约 2.0 mm | 第一次 -16，减速后成功，实际抬到约 z=-0.343 |

当时的代码路径是 `finish_servo_grasp` 合爪成功，双手同时抓则进入 `finish_to_standby` → `retract_staged` → `arm_vertical_lift` → `staged_retract_line` → `plan_arm_line_from`。竖直抬升会锁当前 J2 调 `Line_Trajectory`，再用 `connect_held_start` 把 SDK 轨迹接到伺服停住的关节上。接不上就半速再来一次。半速只改变采样疏密。

离线复算用的是伺服最后一拍保持关节和同一份 `Robot_Arm_Model.yaml`，目标是当前末端只加 0.08 m：

| | 0.40 m/s | 0.20 m/s |
|---|---|---|
| 右手 | 直线成功，末端误差 0，没有下压也没有水平偏。第 0 点 J3 比保持关节大 0.171 rad（约 9.8°）。连接器拒绝 | 同一个 J3 差，仍然拒绝 |
| 左手 | 第 0 点关节与保持关节重合，但第 0 点加速度 8.28 rad/s²，超过接缝上限 6，连接器拒绝 | 第 0 点速度 0.011 rad/s，低于 0.02 的直通条件，连接器通过 |

这就是现场日志：右手两次 `SDK_start_does_not_join_held_reference`，左手第一次失败、第二次抬起。直线几何存在。锁 J2 并没有锁住整条支，J3 照样换。减速不换支。

思考过程：

- 先怀疑是手相机门限。日志里合爪前已经 `ready_precise`，抬升阶段不再看相机，排除。
- 再怀疑是“简单的直线上升，求解器算不出来”。复算表明求解器算出了完美的末端直线，只是关节不是现在这套。七轴多出来的那一个自由度就是这个缝。
- 曾经想过每 2 mm 解一次再做几何复查，以及走不下去就倒放下降轨迹。这能保证离孔，但把一个积分问题做成了两套检查。雅可比只在一小段上有效，所以必须拆步；拆步之后，IK 残差本身就是检查，不必再叠一套“不许下压、不许横移”。用户指出这一点之后，方案收成大约 10 mm 一段、种子是上一步关节。
- 也想过一次解完 80 mm。现有求解器单次预算大约 0.3 rad，现场一次上抬的关节变化往往更大，一次解不完。
- 放宽 0.05 rad 门槛、或只改写轨迹第 0 行，都会把换支藏进第一拍。零件还在孔里，不做。
- 上 Pink 能根治所有笛卡尔段的选解，但要先有整机模型。这次只缺上抬这一段的连续性，用已有的 `solve_pose_with_fk` 分段积分就够。

落地在 `arm_vertical_lift`，料盘和传送带抓取共用：

1. 起点是伺服停住的关节，没有保持位时用编码器。
2. 水平位置和姿态不动，高度按约 10 mm 增加，直到 0.08 m 或 `grasp_valid.z_max`（-0.05 m）。
3. 每段用 `solve_pose_with_fk`，种子是上一段。相对抓取关节超过 1.5 rad，或相对上一段超过 0.20 rad，这段作废并减半，最小 2 mm。
4. 不用 SDK 的 `Check_Joint_Limit`。右手这次抓取的 J2 大约 74°，模型上限 5°，一查就把已经抓住的构型判死。
5. 先 `take_final_hold` 再播放。若保持还在，连接器会因为巡航速度或加速度再次拒绝一条本来连续的轨迹。左手 0.40 m/s 那次就是这种拒绝。
6. 几乎没抬起来（不足 2 mm）才算失败。能抬一段就停在那里交给收手。

## 第二场故障：上抬成功，收手被同一类选解拒绝

日志：`logs/visual_servo/servo_1793774949056868_70478.csv`，14:49。二进制已经包含连续上抬。

两只手都抬完，腰也升完了：

| | 抓取 z | 抬到的实测 z | 抬高 |
|---|---|---|---|
| 右手 | -0.408 | -0.339 | 69 mm |
| 左手 | -0.416 | -0.344 | 72 mm |

规划记录是 `seeded rise=0.0800 rows=48`，随后 `lift_done`。水平位置基本没动。

收手仍是不锁冗余的 `Line_Trajectory`，再由 `execute_arm_trajectory` 里的 `bridge_from_hold` 去接。规划本身成功：`return_plan code=0`，右手 106 点，左手 92 点。然后 `return_failed code=-16`，发生在 `retract_start` 之前，也就是连接失败，一个点都没发。

用抬升最后一拍指令关节复算到传送带准备位 `(0.45, ±0.25, -0.20)`，姿态 0° / 45° / ±30°，速度 0.40 m/s，不锁 J2。点数和日志一致：

| | 直线 | 第一点和停住关节 | 第一点末端 |
|---|---|---|---|
| 右手 | 成功，106 点 | J5 差 0.257 rad，约 14.7° | 和抬完位置相同 |
| 左手 | 成功，92 点 | J5 差 0.071 rad，约 4.1° | 和抬完位置相同 |

门槛是 0.05 rad，约 2.9°。两边都超过，连接器直接拒绝，还轮不到“不许下压、不许横移”那两条。

为什么以前收手能过：那时上抬也是 SDK 直线。抬成功时手臂停在 SDK 自己选出的关节上，下一段从这个点接着算，第一点通常还是这一套。`retract_staged` 又要求两只手都抬成功才进入收手，所以能进收手的时候，两只手都已经在 SDK 的支上。连续上抬改完之后，停住的是另一套关节，同一末端位姿被重新选解，这次换的是 J5，不再是上抬时的 J3。

思考过程：这和上抬是同一类原因，不是同一步，也不是准备位到不了。末端直线是对的。继续放宽连接器会在空中拧腕，而且左右肘会继续各走各的。用户明确说收手不需要保持末端路径。那就不要再做笛卡尔直线。

回 home 的对照也在这时说清楚。`move_arms_to_home` 最终走到 `arm_line_move`：读电机角，`Line_Trajectory`，直接 `execute_arm_trajectory`。没有保持位，就没有连接器。表播完就算成功，不等 8 mm 和 0.08 rad。SDK 直线末尾有减速，指令结束时手臂通常已经靠近目标。所以“几乎任何位置回 home 都成功”不能证明收手这条带连接器、带短到位窗的笛卡尔路径也该成功。

## 第三场故障：连续收手播完了，左手没在 2 秒里到位

日志：`logs/visual_servo/servo_1793776519109110_81427.csv`，15:15。

这时收手已经改成和上抬一样的连续积分，不再经过连接器。两只手都规划并播放了（左手 143 点，右手 147 点）。右手播完 0.74 秒后 `return_done`。左手播完后再等满 2 秒，`return_failed arrival_timeout`。一边失败，`retract_staged` 整段失败。

左手最后一拍指令的正运动学就是准备位，距离约 0.04 mm。指令刚发完时，实测还在 `(0.499, 0.214, -0.241)`，离准备位 73 mm，J3、J4、J6 还差大约 0.3 rad（约 18°）。右手当时更远，约 100 mm，但随后跟上了。左手这 2 秒里没有同时进入 8 mm 和 0.08 rad。

`return_failed` 那一行里的 xyz 仍是抓取时的位置。`task_event` 抄的是伺服槽里的旧状态，不是超时时新读的正解。能用的实测是 `retract_end`。

思考过程：这条轨迹运动学上到得了准备位，失败记录是到位窗，不是选错支。指令表一直巡航到最后，没有 SDK 直线那种减速尾巴，所以播完时手臂还落后一截。回 home 没有这道 2 秒检查。随后只把收手的到位放宽到 20 mm、0.15 rad（约 8.6°）、4 秒，并每 0.5 秒打印实测、目标和误差。上抬仍是 8 mm、0.08 rad、2 秒。这次放宽没有根治，因为下一场测试在更早的地方失败了。

## 第四场故障：肘不一致，而且下一轮抓取进不了伺服

日志：`logs/visual_servo/servo_1793777898626589_90518.csv`，15:38。二进制是 15:29 那次放宽到位窗的程序。

两只手都夹住并抬高 80 mm。收手：

| | 结果 |
|---|---|
| 右手 | `return_done`，还差 18.6 mm，进了 20 mm 的门 |
| 左手 | `arrival_timeout`，还差 38.3 mm，姿态差 9.6°，姿态过了 8.6° 的门 |

播完时的肘，不是左右镜像：

| | J2 | J3 |
|---|---|---|
| 右手实测 | +35° | -63° |
| 左手实测 | -43° | +31° |

连续积分保留的是各自在孔里的那一支。回 home 会让 SDK 再选一套接近设计姿态的肘，所以看起来“正常”。这里没有那一步，两只手就各停在抓取支上。

这一轮以收手失败结束，抓取循环返回 -37，日志原文是“收手未完成，停止当前任务”。15:38 之后没有新的伺服文件。再点抓取时，程序要先从这套残留姿态摆到拍照位，这一步在 `begin_session` 之前。失败就不会产生手相机日志，看起来像“一进抓取就立刻失败”。终端在 `/dev/pts/1`，没有被这次记录收进去，所以具体摆臂返回码不在伺服 csv 里。

思考过程：到位窗再放宽，也解决不了肘不一致，而且左手 38 mm 已经超出 20 mm，单纯加时间不能保证它还在往准备位走。用户要求收手不保持末端。正确的动作是：准备位只求一次逆解，得到设计好的那组关节，再在关节空间插值过去。左右手因此回到各自的待机构型肘，而不是孔里的肘。`Joint_Trajectory` 中间不再求逆，连接器无支可拒。表播完即成功，和回 home 的成功标准对齐。传送带放置的 `lift_and_retract` 明确保持不动。

## 第五场故障：关节轨迹没生成，因为单点逆解返回 -3

日志：`logs/visual_servo/servo_1793781850865575_113433.csv`，16:44。二进制是 16:24 的关节收手。

上抬再次成功。两只手都是 `return_failed ready_ik`。`Joint_Trajectory` 没有点列，手臂停在抬高后的位置。

`solve_ready_joints` 用待机构型种子（右手 J2 约 45.7°，左手约 -30.9°，这组和回 home 用的待机构型相同）对传送带准备位做了三次尝试，失败后再用当前关节做混合逆解。离线复算和日志一致：

| 种子 | 解析 | 混合 | 数值 |
|---|---|---|---|
| 待机构型 | -3 | -3 | -1 |
| 抬完时的关节 | -3 | -3 | -1 |

右手再把指定 J2 改成 0°、5°、-5°、20°、45°，解析逆解仍是 -1 或 -3。头文件写明七轴的 -3 含关节超限。模型里右手 J2 最大 5°，左手 J2 最小 +5°。准备姿态的肘在 ±45° 附近，解一出来就被这张表丢掉。数值法也只在这张过窄的表里收敛，所以是 -1。

把同一份模型复制出来，只把限位放宽到手臂实际转得到的范围之后，三种逆解全部变成 0。指定 J2=45° 时，右手解出 J2=45°、J3≈-1.2°。J2=0° 仍然是 -1，说明不是任意冗余角都有解析解，而是 ±45° 这一支本来就有，被限位表拒绝了。

这和“直线规划能到准备位”不矛盾。更早的复算里，`Line_Trajectory` 对这个位姿返回 0。单点 `Inverse_Kinematics*` 和整条直线不是同一道门。回 home 走的是后者，所以不受 -3 影响。收手改成“先要一个合法的终点关节”之后，正好撞上更严的那道门。

思考过程：

- 不能承诺任意位姿都有逆解。到不了的点、腕部奇异，仍然应该失败。这个准备位每天都在用，不属于那一类。
- 若直接改 `Robot_Arm_Model.yaml`，抓取和其他逆解也会在更宽的 J2 里选肘，现场会看到肘变怪。用户要求只在收手放宽。
- 伺服的 `enforce_sdk_joint_limits: false` 改不到 `.so` 里面的 `Inverse_Kinematics`。必须给这次调用另一份限位。
- 放宽之后仍把目标 J2 定在待机构型上，而不是“限位内随便一支”。否则放宽本身又会选出怪肘。

## 现在代码里收手实际怎么做

`retract_ik_arm` 在第一次收手时读取 `config/Robot_Arm_Model.yaml`，写到临时文件 `t170_retract_j2_model.yaml`。只改两个数：右手 `joint_limit_max_deg` 的 J2 从 5 改为 90，左手 `joint_limit_min_deg` 的 J2 从 5 改为 -90。其余连杆、工具和限位不动。抓取用的 `Robot_Arm` 对象仍加载原文件。

`solve_ready_joints` 在这份临时模型上求准备位，顺序是：指定待机构型 J2 的解析解、以待机构型为种子的混合解、数值解、再退到当前关节。成功时日志打印 `准备位关节` 以及 J2、J3 的角度。

`play_joint_return` 用这份模型生成 `Joint_Trajectory`。实机模型会把 J2=45° 的终点判成超限，所以不能拿实机对象来生成这段轨迹。若五次多项式仍失败，退回 `make_linear_joint_traj`，也就是回 home 在 `Joint_Trajectory` 失败时用的关节插补。先解除伺服保持再播放，避免连接器插手。表播完写 `return_done joint_trajectory`，不再用 2 秒到位窗取消这段。日志里会有指令末端和目标 xyz。

竖直上抬仍是 `play_seeded_vertical_lift`。传送带放置松爪后的 `lift_and_retract` 仍是原来的两段直线。

## 还没做、也不该混进这次收手的事

- 孔边直线如果还要交给 `Line_Trajectory`，换支会再出现。上抬已经避开了。若希望所有笛卡尔段都不再靠连接器挡，SDK 需要把起点关节做成硬约束，并让冗余连续。这是库的升级，不是再放宽门槛。
- 传送带放置收手没有换。它仍可能在选解或连接上失败。
- 播放仍是开环。关节表若比电机跟得快，表结束时实测还可以落后。收手现在不再因此返回失败，但到位精度不再由那道 2 秒窗保证。
- 腰和双臂仍不在同一次求解里。Pink 或 mink 那一层仍然没接。收手不需要它。
- 临时模型只放宽了 J2 的一侧。若准备位的解还撞上 J4、J6 等其他过窄限位，解析解仍会 -3。这次复算放宽全部限位后 J2=45° 能解出，说明当前准备位卡的是 J2；若以后目标姿态变了，要以新的返回码为准。
- 不能把“每次逆解一定成功”写成目标。工作空间外和奇异仍然没有解。能根治的是：实机到得了的准备位，不再被一张过窄的 J2 表拒绝，也不再因为中途另选一支肘而被连接器取消。
