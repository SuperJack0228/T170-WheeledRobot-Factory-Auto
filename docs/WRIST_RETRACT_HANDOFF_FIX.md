# 合爪后上抬、收手交接修正（2026-10-29）

基于分支 `codex/wrist-servo-v1`、现场版本 `99d9732` 修改。现场现象：手相机修正和抓取基本成功，但刚合爪完成、开始上抬时抖动。本次针对运动指令交接和收手轨迹，不修改下降视觉伺服的 PD、映射、下降速度或合爪容差。

## 已确认的软件问题

1. 原 `repeat_final_hold()` 在锁内复制旧抓取关节角，解锁后才发送。因此即使收手线程已经 `take_final_hold()`，之前复制出来的旧保位指令仍可能晚到，把正在上抬的关节又拉回抓取点。单个电机的 CAN 互斥不能保证整组七关节的所有权交接。
2. 原起点连接函数把小于 0.5° 的偏差直接放过。0.4° 在 5 ms 内跳变，相当于 80°/s 的指令斜率，不能当作没有影响。
3. 原竖直抬升规划强行覆盖轨迹第 0 行，无法消除第 1 行中可能存在的逆解分支差异。
4. 原上抬转收手的接缝使用关节线性插值，仅限制步长；它不能保证接缝速度、加速度连续。
5. 原收手失败可能进入一套不检查结果的备用动作，最终仍返回成功。上层可能在手臂没有收回时继续任务。

这些是源代码和可复现测试支持的软件缺陷。它们与现场现象吻合，但尚不能据此认定现场所有抖动来源已经排除。

## 修改后的执行链路

1. 视觉下降完成后，记录最终关节指令并持续保位。
2. 保位期间，左右手分别预规划收手轨迹；预规划与夹爪动作重叠。仍沿用双手合爪结束后再进入双手收手的调用顺序。
3. 起步使用最终保位关节角作为参考。已从该位置静止起步的 SDK 轨迹直接使用；有小偏差或短暂起始跳变时，用五次多项式连接，匹配两端的位置、速度和加速度。不会只改第 0 行来掩盖差异。
4. 正式接管时，等待该手正在发送的整组七关节保位指令完成，再撤销保位所有权。接管返回后，旧保位线程不能再发送该手的旧位置。
5. 保持原有抓取姿态先上抬，名义抬升量仍为 8 cm，上方工作高度限制仍生效。抓取后上抬和回程当前分别使用 `0.40 m/s`、`0.40 m/s`。这都是笛卡尔规划速度，不代表短距离一定能达到该速度。
6. 在抬升尾部尝试五次多项式转弯。只裁剪末段，并要求起弯位置已经接近完整抬升高度；通过 FK 检查连接点不明显下探、不过度偏离原两段路径。
7. 若找不到满足条件的短转弯，连续播放两段完整 SDK 加减速轨迹，去掉重复端点，不加停留时间。这时拐点附近可能减速到零，不能宣称每次都全程非零速度。
8. 收手成功后，按原流程进入传送带准备位置。失败时报告 `MotionFail=5`，调度执行入口返回 `-37`，保留已持件/已放置结果，不把收手失败当成任务成功。原来未经检查的备用收手分支已移除。

保位线程现在有退出和回收逻辑，不再使用永久 detached 线程。

## 参数

均位于 `config/move_box_params.yaml` 的 `head_grasp`：

| 参数 | 当前值 | 用途 |
| --- | --- | --- |
| `lift_after_grasp_z` | 0.08 m | 抬升目标量，仍受上方工作高度限制 |
| `retract_lift_vel_m_s` | 0.40 | 抓取合爪后的上抬速度，显式保留当前主流程原来实际使用的速度 |
| `return_vel_m_s` | 0.40 | 回传送带准备位置的速度 |
| `retract_connector_speed_rad_s` | 1.5 | 新增连接段的关节速度上限 |
| `retract_connector_accel_rad_s2` | 6.0 | 新增连接段的关节加速度上限 |
| `retract_connector_jerk_rad_s3` | 80.0 | 新增连接段的关节加加速度上限 |
| `retract_connector_max_s` | 0.40 | 单个连接段搜索的最长持续时间 |

后四项只约束新生成的连接段，不是整条 SDK 轨迹或硬件的额定限值。正常 SDK 起步和巡航不会因为超过连接段的加速度设置而被整体限速。默认值尚待真机验证。

旧流程仍有 `lift_vel_m_s`。后续加入的料盘邻孔放置流程已改为独立读取 `tray2_place.retract_lift_m`、`retract_lift_vel_m_s`、`retract_return_vel_m_s`，详见 `TRAY_PLACE_NEIGHBOR_SERVO.md`。新字段缺省有默认值；显式填写零、负数或非有限值会在配置加载时报告错误，不会静默改成一个较快速度。

新的起点连接只处理小幅差异，超过 0.05 rad 的起点差异会要求重新规划或报告失败。连接段会做局部 TCP 几何检查。这些是轨迹一致性检查，不是额外收紧抓取像素误差或合爪门限，也不是完整的碰撞检测。

## 日志怎么看

仍写入 `logs/visual_servo/servo_*.csv`，与原有合爪事件使用相同的 session、hand、task_tag。

- `retract_start`：开始播放收手轨迹。`exclusive_hold_to_trajectory` 表示已经独占接管。
- `retract_sample`：最初 250 ms 每条指令记录，之后每 20 条指令记录一次，当前名义周期为 5 ms，约为 10 Hz。
- `retract_end`：轨迹播放完成，表示最后一条指令已经下发，不等于独立测量证明电机完全到位。
- `retract_abort`：播放中遇到 STOP 或 CAN 故障。规划失败或调用异常也需要结合 `startup.log` 的左右手返回码查看。

新增列：

| 列 | 含义 |
| --- | --- |
| `trajectory_row` | 播放行号 |
| `command_q0..6` | 当次下发的七关节角，rad |
| `command_step_rad` | 与上一条指令相比，变化最大的关节角；开始行与交接的保位指令比较 |
| `command_speed_rad_s` | 按名义播放周期计算的最大关节指令速度 |
| `command_accel_rad_s2` / `command_jerk_rad_s3` | 相邻指令差分得到的加速度/加加速度，按名义周期计算 |
| `dt_ms` | 本条与上一条命令周期起点的实际间隔；周期首行不适用 |
| `hold_release_wait_ms` | 等待保位发送结束并移交所有权的时间 |
| `joint_feedback_valid` | 本行是否实际读取了关节反馈 |

只在收手开始和结束读取反馈，播放循环内不额外读取 CAN、不直接写文件。没有实测反馈的行，`actual_q`、实际 TCP 和速度写 NaN；不要把缺失数据当成零。指令差分反映的是指令连续性，不是实测振动。终端还会打印每只手整个收手轨迹的指令步长、速度、加速度、加加速度峰值；SDK 巡航段峰值可能高于连接段限制。

汇总工具已支持收手事件和旧 CSV：

```bash
python3 tools/analyze_visual_servo.py logs/visual_servo --json servo_summary.json
```

新增 `retract` 汇总：合爪结束到开始收手的间隔、保位释放等待、起步指令跳变、播放周期，以及开始/结束的关节跟随误差。没有新事件的旧日志会显示 `retract: null`。

## 编译和现场验证

在机器人工作目录重新编译，沿用原启动命令：

```bash
cmake -S . -B build_robot
cmake --build build_robot -j4
./build_robot/t170c_debug 2>&1 | tee startup.log
```

按现有双手单次抓取方式验证，先保持当前 YAML 值。重点看：

1. 刚合爪后，上抬是否仍出现那一下抖动；上抬与收手是否有可见卡顿。
2. 终端的 `corner=quintic` 或 `corner=sdk_profiles`：区分使用了平滑转弯还是完整 SDK 加减速轨迹。
3. 两手对应的 `retract_start` 首条指令是否与保位连续，随后周期是否出现异常长间隔。

反馈时保留完整 `startup.log`、本次生成的 `servo_*.csv` 和实际 YAML；如果有视频，包含合爪前后至收手结束即可。无需为本次改动额外重复相机检测或整机定位精度试验。

## 本地验证范围

- 使用实际 `runtime.cpp` 的并发回归：阻塞旧保位的发送，验证所有权交接必须等待该发送完成，之后重复保位不能再写旧目标。同一测试在修改前版本上会失败，在修改后版本上通过。
- 数学轨迹回归：0.4° 小跳变、被第 0 行掩盖的第 1 行跳变、SDK 正常起步保留、五次曲线端点导数、连接段速度/加速度/加加速度边界和无效输入。
- 生产配置加载器回归：实际 YAML、外置参数实际生效、旧 YAML 缺省、新字段错误值；原视觉控制回归继续执行。
- 已检查运动相关改动文件的 C++ 语法，以及新旧 CSV 的汇总和列对齐。

Mac 本地未链接完整 Linux 硬件 SDK，也没有运行真机。上述验证不能替代双手现场验证；本次修正提供的是明确的软件修复和可追踪日志，不是对真机“保证不抖”的承诺。
