本次提交将 `Approach_Stroke` 的 A→B 接近余量也改为 150 mm；新增夹爪准备开度回读及异常码 1404；传送带放置等待前一只手进入回程后再允许另一只手进入；终端和伺服记录按日期归档。

上传的 `field_logs/20261124` 包含双手传送带抓取、放置和撤离成功记录，两个 CSV 合计有 5 个伺服会话以 `ready_precise/done` 结束。日志中的三条非成功技能结果为 `native_code=-4`、状态 `cancelled`，其中有撤离 `abort` 记录，不能直接统计为规划失败；日志也不足以确定每次取消的外部触发来源。

这些日志的服务就绪标记是维护模式，未出现新夹爪准备开度打印或 1404 处理记录。它们不作为最新 1404 恢复分支和整套自动调度任务已经完成验证的证据。已有离线测试确认 1404 的本机映射，正式自动运行前还需与调度确认其识别、处理及恢复约定。

## 3. 打包前需要收口的事项

### 3.1 持久配置与运行快照分开

当前网页运动参数入口直接写运行目录的 `config/move_box_params.yaml`，并调用 `reload_config`。该文件由源配置合成，下一次启动会重新生成，网页修改不会自动写回源参数。

V1 应形成一条完整链路：

```text
单机 quick_params.yaml
    → 与版本默认值、机型、场景及单机档案合成
    → 校验候选配置
    → 空闲时事务式提交并重载
    → 保存持久文件及本次运行快照
    → 重启后仍使用相同调参值
```

建议将常改项集中到当前机器人自己的 `quick_params.yaml`，包括抓放 XYZ 偏置、悬停/抬升高度、动作速度及夹爪准备开度。编号、相机 SN、3/5 kg、TCP 和手眼仍归单机档案；控制默认值随程序版本发布。稳定默认值可以作为只读 YAML 随包安装，不必全部硬编码进 C++。

现有部署生成器禁止不同层重复拥有同一个键，直接追加一个同名参数文件会报 `Ambiguous duplicate ownership`。快捷文件需新增明确的覆盖阶段和字段范围，并在配置来源记录中标明最终值，不能仅创建同名文件。网页保存应落到这份持久文件，失败时回滚文件和运行配置。四份抓放任务标定目前通过单机标定目录链接保存，这部分持久化机制可复用。

### 3.2 头相机标定入口统一

当前 No.124 的 `head/geometry.yaml` 为：

```yaml
camera_to_head_yaml: extrinsics_urdf.yaml
```

C++ 实际按此字段读取文件，而网页手眼编辑和旧指南默认操作 `extrinsics.yaml`。因此，导入或编辑 `extrinsics.yaml` 不代表当前计算已经切换到该文件。

第二台机器人使用实测头部手眼时，应导入该机 `head/extrinsics.yaml`，将其 `geometry.yaml` 改为 `camera_to_head_yaml: extrinsics.yaml`，并让网页显示和编辑实际选中的文件。当前模板还映射 `extrinsics_urdf.yaml`，选择实测文件后应移除不再使用的映射或提供对应文件，避免生成器因缺少未使用资源而拒绝启动。No.124 当前已验证配置不在此复核中改动。

### 3.3 安装布局及启动路径

目前缺少应用的 `install()` 清单和 CPack 配置。主程序位于 `build_robot`，安装 RPATH 仍包含构建仓库的 SDK 路径；运行目录将 Python、权重、网页和程序链接回资源树；systemd 模板写有 `/home/ti5robot/T170Clean`。直接拷贝一次运行目录不能成为独立运行包。

封装需补齐：

- 将主程序、配置校验器、所需动态库、Python、网页、权重和配置模板安装到明确的位置。
- 包内库按安装位置查找，外部 `/opt/ti5-*` SDK 与 Python 环境按发布清单匹配，避免依赖构建者的仓库绝对路径。
- 将版本文件、单机配置和日志/运行数据分开。日志不能默认写到只读程序安装目录。
- 启动器、网页及机器人档案管理支持安装布局，不再要求 `build_robot` 存在。
- 从一个全新的目录测试安装包，并在原源码目录不可用时验证配置生成、程序加载和网页资源。

可以保留运行快照指向已安装只读资源的链接；需要消除的是对开发源码树和临时构建目录的依赖。

### 3.4 固定运行环境和版本记录

当前 `python/requirements.txt` 只有最低版本，外部 SDK 清单没有安装版本；C++ 嵌入 Python 还绑定构建时的 Conda 环境。应从 No.124 已工作的环境记录 SDK 包版本、Python 小版本、PyTorch/CUDA/Ultralytics、RealSense、OpenCV、系统及架构。

首版不更换已经验证的推理环境。在匹配 No.124 的 Linux ARM64 环境生成二进制；Mac 构建结果仅用于离线检查。3/5 kg 配置由同一个程序选择，5 kg 的实机能力另行确认，不以配置生成通过替代实机验证。

发布文件至少包含应用版本、Git commit、构建环境、SDK/Python 依赖版本、支持机型、在用权重及文件 SHA256。修正部署测试基线后重新运行全套检查。

## 5. 从冻结代码到发布

### 第一步 冻结候选版本

将经过现场确认的控制代码、参数和标定一起提交，完成本节前述发布收口，确保工作区干净。给候选版本建立 `v1.0.0-rc.1` 标签。运行包必须记录该标签指向的 commit，不从持续变化的分支随意取文件。

### 第二步 在目标兼容环境构建

在 No.124 或同环境 Linux ARM64 构建机执行现有构建命令：

```bash
cmake -S . -B build_release -DCMAKE_BUILD_TYPE=Release
cmake --build build_release --parallel 3
```

封装接入 `install()` 与 CPack 后，发布构建继续执行：

```bash
cpack --config build_release/CPackConfig.cmake -G TGZ -C Release
```

当前还没有 `CPackConfig.cmake`，最后一条命令须在封装实现后使用。CPack 按 CMake 的安装清单生成二进制包，不会因为存在 `packaging` 文件夹就自动收集正确的运行文件。

### 第三步 验证实际生成的安装包

使用包本身完成一次换目录安装和依赖加载检查，再在 No.124 执行准备位、料盘抓取、传送带抓放、料盘放置及正常撤离。用调度驱动一次上料、转运和下料，并确认 1404 的异常处理约定。检查网页调参保存后重启仍保留，标定文件仍属于当前机器人。

程序的 `--help` 和配置校验器可用于不驱动硬件的安装检查；维护入口也会初始化硬件，不能当作纯离线检查命令。合格结果保存为该候选包的验证记录。

### 第四步 发布候选包

在 GitHub 为 `v1.0.0-rc.1` 创建预发布，上传自行生成的 ARM64 运行包、SHA256、发布说明和依赖记录。GitHub 自动生成的 Source code ZIP/tarball 是源码快照，不是本项目编译后的运行包。

Release notes 写清支持的系统环境、3/5 kg 配置方式、单机配置位置和已知限制。内部维护符号可另存，运行包不必携带 C++ 源码及调试数据。

## 6. 第二台机器人部署

以下步骤针对已经完成上述封装的运行包；当前源码部署仍使用现有 [新机快速指南](NEW_ROBOT_DEPLOYMENT_GUIDE.md)，并按第 3.2 节修正头部标定文件选择。

### 第一步 安装运行包及匹配 SDK

第二台机器人保持与发布包相同的系统和推理环境，安装发布清单指定版本的设备与调度 SDK。本机运动学库由运行包提供。沿用公司 APT 源，SDK 包名为现有指南中的 `ti5-device-sdk`、`ti5-jindi-faactory-robot-client`，具体版本以该运行包的清单为准。

```bash
sudo apt update
```

这条命令只刷新 APT 索引。下载 GitHub Release 的二进制包并校验 SHA256，解压到新的版本目录，由安装入口建立 `current` 和可写配置/数据目录。第二台机器人不再编译 C++，也不需要手工拷贝开发机的整个源码目录。

### 第二步 建立本机档案

以 No.125 为例，录入实际编号 `TH-T170C-0125`，选择 `t170c_v2_3kg` 或 `t170c_v2_5kg`，填底盘地址和三台相机 SN。编号必须同时匹配部署档案的 `robot_id` 与身份文件的 `chassis.sequence_number`。同环境同场景的站点、动作参数和模型默认值复用模板。

配置应归本机持久目录，默认选择入口为 `deployment.yaml`。新机安装流程不默认选中 No.124。型号变化会重新生成模型配置和坐标转换，重启生效，不需要为 3/5 kg 单独修改算法。

### 第三步 导入本机几何和标定

| 内容 | 当前仓库中的对应位置 |
|---|---|
| 头相机到头部末端 | `config/calibration/TH-T170C-0125/head/extrinsics.yaml` |
| 头部几何与实际文件选择 | 同目录 `geometry.yaml`，`camera_to_head_yaml` 指向实测文件 |
| 左右手相机到法兰 | `config/calibration/TH-T170C-0125/hand_eye/left.yaml`、`right.yaml` |
| 头相机到基座的静态备用矩阵 | 同目录 `head_fallback.yaml` |
| TCP 和 IO 角度约定 | `config/robots/TH-T170C-0125/arm_tools.yaml`、`arm_binding.yaml` |

工具、设备和运动角度约定与 No.124 相同的部分可复用；实测手眼使用本机文件。标定格式沿用工程约定，矩阵平移单位为 mm。手相机标定若属于新 SDK 法兰，档案标明 `sdk_flange`，避免重复应用旧法兰转换。

### 第四步 维护模式完成四份参考标定

启动维护服务和网页，在标定向导完成本机左/右抓取、左/右放置四份参考：

```text
calibration/TH-T170C-0125/tasks/grasp/left.yaml
calibration/TH-T170C-0125/tasks/grasp/right.yaml
calibration/TH-T170C-0125/tasks/placement/left.yaml
calibration/TH-T170C-0125/tasks/placement/right.yaml
```

这些参考包含相机内参、实际 TCP 姿态、参考像素和几何指纹，不能把 No.124 的结果改个编号就当作新机结果。当前生成器允许这四份结果缺失时进入维护配置，供新机完成标定。

封装后的启动入口保留维护、生产、网页三种用途，具体命令随运行包一并提供。当前源码已有命令分别为 `./deploy/run_maintenance.sh`、`./deploy/run_production.sh`、`./deploy/run_web.sh`；不能将源码脚本路径直接冒充尚未生成的二进制包入口。

### 第五步 调整快捷参数并验证一次闭环

有机械装配或场景差异时，修改本机 `quick_params.yaml` 中的高度、偏置和速度。验证保存重启后仍生效，执行双手抓取、传送带抓放和料盘放置，再通过调度完成一次上料、转运、下料。记录单机配置和标定版本。

### 第六步 切到生产入口

停止维护服务，启动生产服务并由调度分配任务。网页仍可观察运行状态。配置 systemd 开机入口时使用实际安装路径，保留当前不在任务失败后自动重启并重新 Home 的策略。

候选包在 No.124 和第二台机器人完成上述验证后，冻结对应 commit 发布 `v1.0.0`。单机差异保存到机器人配置包，不再复制修改核心源码。

## 7. 后续升级与回退

程序更新安装到新的版本目录，停止任务和服务后切换 `current`，重新生成运行快照。升级前备份单机配置及标定；安装器不覆盖这些文件。配置存在格式变化时，使用明确的迁移步骤。

回退时选择上一版本，同时恢复与该版本兼容的配置快照，再启动服务。仅切换程序文件不保证新格式配置能被旧程序读取。日志保留实际应用版本、Git commit、机器人编号、模型、配置和权重指纹。

首版使用 Release 二进制包即可；以后可以基于同一安装清单生成 `.deb`。GitHub Release 不会自动成为 APT 源，只有另外建立软件仓库、索引和客户端源配置后，才可以用 `apt install/upgrade` 更新本应用。
