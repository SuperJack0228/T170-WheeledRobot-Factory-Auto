# 严格三步迁移计划

基线：`e205e9e`。当前基线已包含11月3日现场伺服修复；公共组件与 `t170_factory` 更名作为起点，后续正好三步。每步可以拆成小提交；本文件里的“完成”指验收出口通过，不以文件搬完为准。

本地代码实现和外部环境验证可以并行。缺少匹配 SDK/真实模型/现场验证时，相关项标记为“已实现，待外部验证”，完成本地检查后可以继续后续代码工作，不要求在家中连接机器人。第三步正式发布前必须补齐这些证据，不能以本地语法检查替代。

## 第一步：底层模块归位与依赖整理

目标：把已经成块的代码放到明确位置，先形成可构建的 vision/control/hardware 基础。完整清单对应迁移表中 step=1。

顺序：

1. 抽出必要的帧、时间、观测、几何/结果类型，保持现有数据和时钟含义；规划新公开头文件与旧接口转发。
2. 迁移纯控制核心、局部求解及专用 trace/计时；不改 PD、像素映射、制动、下降协调和收手曲线。
3. 整块迁移总线、夹爪、头、腰和 LowerBody；原 SDK、设备映射和模型参数保持。
4. 按 camera/detection/geometry/tracking/bridge 整理 C++ vision；把手相机观察与电机发送权限分开，已有串行公平推理和采集时间策略保持。
5. 将 Python 代码收进 `t170_vision`，整理包内导入，避免多个 `online.py` 同名冲突。权重/板参数的实际切换仍由后续配置/资源迁移负责。
6. 更新 CMake 目标、头文件与导入烟测，记录暂时兼容入口及尚在大文件里的调用点。

交付：底层模块代码和公开头文件、可离线构建的控制核心、明确的依赖图、更新后的迁移表和兼容清单。

出口：

- 原九项离线回归保持完整并通过；改了观测接口时补查 session、采集时间、左右手和目标身份。
- Python 从新包可导入，配置给出的头/手模型仍对应原角色与类别；缺模型时清晰失败。
- 完整程序在匹配的 Linux/ARM64 SDK 环境编译通过。Mac 检查只作为辅助证据。
- 没有参数重调，没有新旧两套控制算法；观察线程仍不能下发电机命令。
- 过渡组装目标可以保留，但具体依赖和临时适配有登记；不能以隐藏循环依赖作为完成状态。

此步不改变现有业务顺序，不实现 RL，不切换 ROS 2，不新增检测模型。

## 第二步：动作任务拆分与参数独立

目标：把大文件拆成 motion/skills/tasks/integration/app，并完成可部署参数的真正独立。完整清单对应 step=2；这一步工作量最大。

顺序：

1. 将 `function.cpp` 分成位姿/单位工具、SDK 规划适配、轨迹播放、状态回读、局部求解、撤离衔接和演示动作。
2. 将 `servo/runtime.cpp` 归为 motion 的伺服执行器，统一读反馈、发送和最终保位交接；每只手一个发送所有者。
3. 将料盘/传送带技能分开，共用接近、闭环下降、保位、夹爪反馈和撤离原语；保留先计数、一手一个、先右后左等现有规则。
4. 拆开 `robot_runtime.cpp`：任务流程进 tasks，调度协议进 integration，导航/电量/充电设备接口进 hardware，音频/应用生命周期有各自归属。
5. 主程序只组装和启动。RobotContext/任务会话拥有设备、状态和配置，逐步替换散落全局；原命令/端口及中止约定保持。
6. 按 [参数独立方案](PARAMETER_OWNERSHIP.md) 拆分全部生效参数。把代码中的夹爪初始化、传送带窗口、调度地址、设备映射等可部署差异补齐，不能只拆原 YAML。
7. 建立显式 deployment 选择、schema/单位/坐标系校验、最终生效配置与来源清单；同输入与旧版对照，保留每个旧值及启用开关。
8. 每次动作持有同一不可变配置快照；重载先完整校验，再在约定边界切换。静态设备/模型需重启；运动参数下一动作生效；确需在线改变的业务阈值使用独立一致快照。
9. 同步网页、CLI、诊断和预检工具，避免界面改的是旧文件或与机器人使用不同参数源。

交付：职责单一的运行模块、统一抓放和运动接口、独立参数目录、加载/校验/快照机制、当前机器人与场景的真实配置、已消除循环依赖的构建图。

出口：

- 不能留下一个新目录里的大型 `robot_runtime.cpp` 继续包办全部职责，也不能仅按行数切成多个互相 `extern` 的文件。
- motion/vision/control/hardware 之间没有命令双写或 CMake 环依赖；任务和技能不直接调用设备协议细节。
- 现有配置迁移前后生效值等价，逐行偏置的启用状态保持；失败加载和错误机器/标定不会切换到部分配置或另一机器资源。
- 单次动作不会混用新旧配置，设备 ID/相机 SN、分辨率/旋转/参考像素和标定版本具有关联校验。
- 原回归、边界接口、错误返回/持件状态和抓放交接检查通过，并完成匹配 SDK 全量构建。
- 未来切换到同型号另一台机器人，改动集中在 robot/calibration/deployment；同型号共用软件不改源码。仍需该机器的真实标定与现场验收。

自动手眼标定、自动系统辨识不属于本轮必须新增的算法；配置必须能导入、校验和记录以后这些工具产生的结果。

## 第三步：资源收口、安装打包与发布验收

目标：形成干净的工程仓库和真正能安装交付的候选版本。完整清单对应 step=3。

顺序：

1. 整理模型、音频、第三方库和 SDK 的实际来源、平台、版本及哈希；补齐所需真实手模型，确认模型类别/输入尺寸/工具配置配套。
2. 将散落资源迁入 assets/third_party，确认实际标定与板几何已进入配置体系；每次改路径同步更新 C++、Python、网页、启动器、诊断和会话快照。
3. 完成 Python 安装元数据、经过验证的环境约束和 CMake presets。记录机器人 OS/架构、编译器、SDK、Python/Torch/CUDA/驱动基础环境兼容性。
4. 整理 tests/tools/deploy/docs；仅在运行引用与恢复用途核验后清理废弃实现、旧转发、备份和过期配置。保留必要历史证据，新增运行输出不再作为源码跟踪。
5. 实现 CMake `install()` 与 CPack TGZ/DEB，产物包含实际程序、Python 包、资源清单和运行说明；单机配置/标定/状态/日志与应用分离。
6. 配置安装不覆盖现场数据；静态库与动态库路径不依赖旧源码目录。安装脚本不自动归位、不自动开始任务。保留现有受限重启策略。
7. 加入离线回归 CI、匹配 SDK 的构建检查和制品清单。实机动作由现场明确触发，不能由普通代码提交自动驱动机器人。
8. 在干净安装目录/匹配环境验证预检、升级、配置保留和回滚；同一候选制品在当前机器人验证料盘抓放、两条传送带抓取、双手交接、空抓和中止恢复。
9. 固定提交/版本、软件与模型/配置/标定/环境清单，发布候选包和验收记录；满足 [发布验收表](RELEASE_ACCEPTANCE.md) 后定版。

交付：规范源码仓库、完整参数体系、安装树、TGZ/DEB 候选包、版本/依赖/模型清单、CI、部署/升级/回滚说明及验证记录。

出口：

- 主程序离开源码目录可运行；没有依赖旧的 `feeding_*`、`board_*`、`free_calib`、`lib`、`eigen3` 或个人工作目录的隐藏路径。
- 保留 SDK/Conda 等基础环境依赖时，明确列版本和供给方式；不能宣称包已包含所有依赖。
- 参数、模型、标定和 SDK 缺失/不兼容在动作开始前明确报告；没有假权重或示例矩阵代替现场文件。
- 现场配置和标定不会被安装/升级覆盖；回滚同时核对配置 schema 与兼容版本。
- 文档只指向当前版入口和参数；旧说明进入 archive，必要历史日志另行归档。
- 第三步的本地工程任务可以先完成，但正式发布须有匹配 SDK 构建、完整资源和实机验收证据。缺少这些时状态是 RC，不是正式发布完成。

## 每一步内的工作方式

每个小提交只做一种主要改动：代码归位、接口切换、配置迁移、资源路径、清理或打包。先保留行为再验证，算法调优单独提交。更新 module_migration.csv 的状态与验证记录；一个大文件包含多个迁移组时，按职责处理剩余部分。

旧代码删除放在第三步收口。每步结束保留可恢复提交和已用配置/依赖记录；没有用户要求时不擅自推送或操作远端发布。
