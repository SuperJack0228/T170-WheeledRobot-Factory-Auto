# 当前执行流水线、语言桥接与并行边界

更新：2026-11-18。描述当前源码；并行推理、TensorRT 与 ROS 2 适配属于后续路线，未在本轮实现。

## 两条命令入口

自动任务：外部调度 → 厂商 RobotClient → `integration/dispatch` → 收信线程/任务循环 → `tasks`。

网页维护：浏览器 HTTP → `web_debug/server.py` → 本机 TCP `127.0.0.1:8099` → 一行 JSON 请求 → `app` 权限和动作互斥 → 标定或单步技能 → JSON 回复。

这两条入口不是同一网络通道。自动调度任务不是逐步通过网页 JSON 服务运行。图像和伺服关节指令也不通过该服务高频传输。

## 一次任务的主要阶段

1. 启动合成运行配置，C++ 校验，创建新 SDK 双臂并回读 DH/工具，初始化设备、相机和 Python 引擎。
2. 生产模式进入调度，核对地图、读取本次任务和动态工位；任务层组织导航、作业申请和异常反馈。
3. 到达取件位置后，头部感知提供目标/工件数量/料盘或传送带几何信息。
4. 技能层选择左右手及目标，计算粗目标和固定末端姿态，规划伸手与下降交接。
5. 接近和下降阶段启用手相机观察；运动线程和视觉线程异步工作。
6. 控制器结合带时间戳观测与实际反馈计算 XY 修正、制动及下降速度；运动层转为关节参考并下发。
7. 满足本任务完成条件后，停止视觉接管并保持最后关节参考；夹爪动作、反馈判断、竖直抬升和后续姿态衔接按技能执行。
8. 技能返回逐手动作、持件、撤离和错误信息；任务决定是否继续导航/放置/恢复，并通过调度客户端报告阶段及最终结果。

上料是料盘抓 → 传送带放，转运是传送带抓 → 另一传送带放，下料是传送带抓 → 料盘放。传送带放置当前默认仍为开环目标，不计入手相机闭环能力。

## 取图与 Python 输入

RealSense 后端管理头、左手、右手的设备与流。头相机采集彩色/深度并对齐；手相机只开启 BGR 彩色流。数据封装为 `CameraFrameData` / `Frame`：宽高、BGR 字节、可选米制深度、K、畸变、帧号和设备/主机时间信息。

手观察线程按需调用 `grab()`，临近推理时才取图；相机 SDK 的底层采集线程与本应用的观察线程是不同层次。当前不能把“取到下一帧”等同于零延迟。

头部流水线可通过 `grab_head_fused()` 清理旧帧后获取多帧。料盘感知中，YOLO 与码检测尝试并发，再利用缓存结果求料盘位姿/孔位。PnP、mask、框中心算法仍保留，但不同任务按配置选择，不能视作每次全部执行。

`SegPoseBridge` 仍存在，位置为 `src/vision/bridge/python_bridge.cpp`；其角色由模块接口包裹，而非被 ROS 或网络服务替代。启动时使用 pybind11 嵌入解释器、导入 `t170_vision`，创建头/手两个引擎并预热。

`python_arrays.h` 将 BGR 转为 NumPy `uint8[H,W,3]`，深度为可选 `float[H,W]`，K 为 `double[3,3]`，畸变为向量，再构造 Python `AlgorithmInput` 并调用 `engine.run()`。内部颜色顺序是 BGR，Python 检测器再按推理框架要求处理。

Python 返回 `AlgorithmOutput.targets`，目标含类别、置信度、框、成功状态和可选位姿等字段。C++ 逐项转回 `PoseRunResult` / `PoseTargetResult`，然后由 C++ 检测接口、目标选择或观察器使用。错误会转为错误信息，不跨语言直接操纵电机。

这不是将大图编码为 JSON 再发给另一个 Python 服务。也不能称为端到端零拷贝：RealSense 帧已复制为 vector；当前 NumPy 构造传指针但未传持有者 base，常见 pybind11 实现会再复制。具体优化应核对目标版本与测量，不能直接换成裸指针共享而忽略生命周期。[pybind11 NumPy 文档](https://pybind11.readthedocs.io/en/stable/advanced/pycpp/numpy.html)、[2.13.6 构造实现](https://github.com/pybind/pybind11/blob/v2.13.6/include/pybind11/numpy.h)。

## 手相机观测与闭环

左右手观察由一个 worker 公平轮询，工作期间以条件变量短等待，未激活时较长等待；它不是无休止空转。观察器先取得会话配置、确认姿态和阶段，再取图。左手图像旋转 180° 并同步调整内参。

抓取通常调用手模型，按类别、置信度、预测位置和上一帧关联锁定目标，形成带帧号、捕获时间和像素位置的 `PixelObservation`。

料盘放置在邻孔路线开启且目标有效时，直接进入 C++ 孔环/邻孔/部分孔环定位器，不走抓取 YOLO 框中心回退。它利用已知料盘几何、实际捕获时刻相机位姿和可见结构，输出被遮挡目标的虚拟像素。

观察提交给 motion 会话。控制侧用状态历史插值匹配图像捕获时刻，进行映射和延迟补偿，再由控制器输出连续参考。新的关节参考经过局部 IK、速度/加速度等约束处理，最后在 `arm_io` 转成设备角，通过设备 SDK 位置接口发送；反馈按反方向转换成模型角，形成闭环。

三条路线的阶段并不完全相同：料盘抓取按观察/下降/修正推进；传送带抓取当前在接受 10 次有效观测后锁定目标，已有目标但观测超时的分支也会锁定，之后不再请求新图；料盘放置当前 `observe_at_B=true`，在高位观察对齐并确认后再下降，临近遮挡阶段锁定目标。不能将它们都描述成一直推理到夹爪动作结束。

普通轨迹采样 5 ms，伺服目标周期当前配置 10 ms。它们是目标时间基准，实际周期还受求解、总线和 OS 调度影响；不代表视觉有 100 Hz 或系统已经达到硬实时。

## 为什么当前推理仍串行

`SegPoseBridge::run()` 中存在一把函数静态 `yolo_mu`，头和手两套模型共用；进入 Python 还需取得 GIL。两个手相机共用手模型，所以多开观察线程却继续共用该模型和锁，仍会串行，甚至增加排队和图像时效问题。

GIL 限制 Python 字节码并行，但 PyTorch/OpenCV 等原生计算可能释放 GIL。不能说 GIL 让 GPU 一定串行，也不能说移除 GIL 就让单块 GPU 速度翻倍。共享预测器的可变状态另需保护。[Ultralytics 官方线程安全说明](https://docs.ultralytics.com/guides/yolo-thread-safe-inference/)。

当前更值得比较的路线为：

| 路线 | 预期价值与代价 |
|---|---|
| 事件唤醒、左右各最新帧槽位、单个推理消费者 | 减少等待/旧帧，模型管理简单；不承诺推理计算本身加速 |
| 同一模型 batch=2 | 双手同时工作时可能提高吞吐；不要为了凑齐两手等待，应有短等待上限并支持单手 |
| TensorRT FP16 | NVIDIA 硬件适合时优先实测；需验证算子、框/置信度、输入输出和目标系统兼容性 |
| 每手独立实例/执行上下文及 CUDA stream | GPU 有余量时才可能降低双手延迟；显存、资源争抢和维护成本增加 |
| 独立视觉进程 | 改善 Python 故障隔离，便于独立升级；需新增共享内存/IPC、时间戳和队列管理 |

比较时记录端到端图像年龄、每手更新间隔及高分位延迟，不能只比较总 FPS。NVIDIA 对多流共享资源、吞吐与延迟取舍有专门说明：[TensorRT 优化指南](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/optimization.html)。本轮没有修改推理后端或取消推理锁。

## 本机服务与 ROS 2

当前本机服务相当于程序的简易操作窗口：定义命令、接收 JSON、在本进程执行，再返回结果。优点是依赖少、调用直接，适合现有网页/单步维护；其协议、进度、版本和错误约定需由本项目维护。

ROS 2 提供机器人组件的标准通信和工具体系：节点表示功能单元，Topic 适合持续数据，Service 适合短请求，Action 适合带反馈及取消的长任务；节点可以同进程、跨进程或跨机器。节点不一定等于一个独立进程。[官方节点说明](https://docs.ros.org/en/jazzy/Concepts/Basic/About-Nodes.html)、[Action 说明](https://docs.ros.org/en/jazzy/Concepts/Basic/About-Actions.html)。

类比：当前服务是给一个车间定制的操作窗口；ROS 2 是一套统一的工单、广播、地址和记录规范。算法和实际执行设备仍需各模块实现，不会因为换通信方式自动提高抓取精度。

未来 ROS 2 适配可放在现有技能接口外：抓取/放置映射为 Action，短查询映射为 Service，关节和目标状态映射为 Topic；保留现有局部控制循环。若引入图像 Topic，应设置小队列及适当 QoS，避免把可靠积压当作实时性。[官方 QoS 说明](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-Quality-of-Service-Settings.html)。

ROS 2 有成熟的标准消息、坐标变换、录制/回放、可视化和仿真生态；代价是消息边界、构建环境、执行器及 QoS 等配置复杂度。它支持进程内优化，不应一概说一定比直接调用慢；也不自动提供硬实时，仍需设计线程、内存和调度。[官方实时编程说明](https://docs.ros.org/en/jazzy/Tutorials/Demos/Real-Time-Programming.html)。

行业例子：宇树公开的 [unitree_ros2](https://github.com/unitreerobotics/unitree_ros2) 将 DDS/SDK2 与 ROS 2 通信接通。这证明可以把底层 SDK 和上层生态组合使用，不能据此推断所有企业内部软件都采用同一架构。
