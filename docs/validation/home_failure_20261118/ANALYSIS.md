# 2026-11-18 双臂 Home 与标定接近失败分析

> 本文件保留修复前的分析及原始结果。后续已实施 Home/限位/求解修复，当前行为见 [运动策略](../../deployment/ARM_MOTION_POLICY.md)。`reference_replay.txt` 是修复前结果；重新编译 `replay.cpp` 使用当前工作区源码，不会自动还原旧算法。

## 1. 范围与结论

代码基线：`deployment1117`，`7213bea`。现场记录为 `docs/problem_note_20261118.md`；保留该文件原文，不采用其中的原因描述代替终端证据。

本次已确认的主要问题集中在应用层运动学适配、构型选择、分阶段运动及反馈传播。当前证据不足以将问题归结为机器人硬件能力不足，或交付动态库整体不可用。

| 问题 | 证据与判定 |
|---|---|
| 相同 Home TCP 对应不同全臂姿态 | 两次右臂 Home 末端都到达目标，但 J1/J2/J3 不同；缺少明确的 Home 关节构型与偏好姿态目标 |
| 固定姿态平移、上抬失败 | 用现场打印关节角及本地同机型模型复现，局部数值求解接近 J6 下界后失败；终点换种子可解，不等于原直线路径已验证可行 |
| 左臂规划目标与实际运动不一致 | 第二次 Home 的左 J7 命令可由编码器差值反推为约 −97.54°，实际停在约 −89.8°；模型允许约 −127.77°。设备实际运行限制尚未读回 |
| 前段失败仍执行后段 | Home 多阶段函数仅累计 `ok=false`；上层直线函数忽略到位等待失败，仍返回轨迹发送结果 |
| 动作多、长时间等待 | 继承的多阶段笛卡尔返回路径，加上默认 15 s 停稳超时和末端原地大幅转姿态，可解释观察到的长节拍；日志无统一时间戳，不能精确分摊全部 20–30 s |
| 标定页面无图 | 头相机检码成功；图像读取依赖 Web 与机器人相同 runtime。现场笔记描述目录不同，源码支持该故障机制；尚缺 Web 启动输出及 HTTP 错误来独立核定具体请求 |
| 标定接近失败 | `move_d → line(initial) → arm_line_move → Arm::Line_Trajectory`，右手规划返回 −4。未进入后续局部下降和手相机拍照；缺少该次完整起点/目标，尚不能定位具体失败关节 |

本轮只同步远程提交、离线复现、归档分析，不更改生产运动算法、模型限位、调度或设备参数。

## 2. 当前实际执行链路

```text
go_home
  → move_arms_to_home
    → move_arms_retract_to
       ├─ 垂臂：solve_home_joints → arm_joint_move
       └─ 非垂臂：保持姿态抬升 → 平移 XY → 校正 Z → 原地转姿态
                  → 必要时再校正 Z

单段直线：arm_line_move
  → 应用层 Arm::Line_Trajectory
    → TCP 插值 + 应用层 local_inverse + time_joint_path
  → execute_arm_trajectory
  → record_arm_cartesian_arrival（等待结果当前未向调用方传播）
```

`src/motion/arm.cpp` 是应用自有适配代码，不能与 `dependencies/sdk/arm/include/Ti5_Robotics.h` 的原生实现混为一谈。正常直线规划没有调用交付库的 `Ti5_Robotics::Line_Trajectory()`；主要使用交付库 FK，在应用层自己逐点求逆解。因此本次日志中的 `line_trajectory_fail ret=-4` 不能直接解释成“新库原生直线函数报错”。

通用单点 IK 则先调用应用层局部算法，失败后允许调用供应方逆解。交付头文件明确：T7 不传冗余角时的数值逆解采用固定初值。当前适配层只检查模型限位和 FK 末端残差，没有对该回退结果增加相对种子的构型评分。

`log_retract_ik_preview()` 打印的 `Δq_deg` 是单点逆解预览，不是随后逐点直线规划的最终关节轨迹。两条求解路径可能给出不同构型，不能把预览里的某个角度变化直接当成实际下发值。

## 3. 两次 Home 的区别

### 3.1 第一次：末端到位，但没有定义整条手臂应如何摆放

现场记录第 34–46 行：垂臂触发关节返回分支。两臂目标 TCP 是镜像的，但 `solve_home_joints()` 在当前角、零位、历史待机种子之间搜索，找到第一组可用解就退出，未比较肘部高度、左右镜像关系或与标准 Home 关节姿态的距离。

第一次与第二次右臂最终状态如下，角度均为模型角：

| 指标 | 第一次 Home | 第二次 Home |
|---|---:|---:|
| TCP XYZ，m | 约 (0.451, −0.354, −0.102) | 约 (0.450, −0.350, −0.100) |
| TCP RPY | 约 (0°, 0°, 0°) | 约 (0°, 0°, 0°) |
| J1 | −23.5° | +22.9° |
| J2 | −64.3° | −93.4° |
| J3 | +14.2° | −51.7° |
| 模型肘部 Z，m | −0.1073 | +0.0148 |

肘部位置由日志关节角及同一 MDH 链计算，定义与 `arm_fk_links()` 的第 4 级变换一致；不是外部测量。肘部 Z 相差约 122 mm，可以解释“末端明明回到了，肘却翻到上方”。

7 自由度手臂即使固定 TCP 的位置和姿态，通常仍有一个冗余自由度。仅用六维末端误差验收，无法保证全臂构型相同或双臂对称。该问题不能依靠更严格的 TCP 到位门限解决。

### 3.2 第二次：局部求解失败、设备未到位与继续执行叠加

现场记录第 624–661 行：

1. 左臂第一次竖直抬升规划失败，`ret=-4`；右臂成功。
2. 函数没有结束，继续平移两臂 XY。
3. 再次为左臂规划升 Z，规划成功并发送。
4. 左 J7 实际未到命令位置，等待停稳超时，TCP 位置误差约 35.1 mm。
5. 到位失败未从 `arm_line_move()` 返回；后续原地转姿态仍执行。
6. 右臂转姿态成功，但肘部构型与第一次不同；左臂再次规划失败，最终整个 Home 返回失败，不再转腰。

这不是一次独立的“连接器拒绝”。本次直线规划失败发生在播放器和起点连接器之前；右手日志中的 `start_gap_deg=0.0 connector_ms=80.0 result=quintic` 表示对应连接器已成功，不能将其作为此次左臂逆解失败的原因。

## 4. 固定姿态平移为什么会在 J6 附近卡住

`Arm::local_inverse()` 当前实现：有限差分 Jacobian → 阻尼最小二乘增量 → 限制最大增量 → 逐次缩短整组增量，拒绝越界候选。

该算法没有把关节上下界放入求解问题，也没有关节居中、限位回避或偏好姿态项。当增量方向持续要求 J6 越界时，它主要尝试缩小同一个方向，不能主动利用其他关节重新分配运动。接近边界后即可能返回 −4。

3 kg 模型的 J6 下界为 −1.04 rad，即约 −59.5876°。复现输入采用终端打印的一位小数角度，完整结果见 `reference_replay.txt`。

| 场景 | 直线结果 | 外部逐点诊断中首次失败的位置 | 上一成功点的 J6 | 距 J6 下界 |
|---|---:|---:|---:|---:|
| 传送带准备位右臂平移 | −4 | 6 / 26 | −59.3163° | 0.2713° |
| 传送带准备位左臂平移 | −4 | 3 / 25 | −59.5641° | 0.0236° |
| 第二次 Home 左臂抬升 | −4 | 4 / 50 | −59.4960° | 0.0916° |
| 第二次 Home 左臂末端转姿态 | −4 | 36 / 111 | −59.5876° | 约 0.000024° |

这些目标在同一模型限位内，使用其他起始种子均可求出终点。该结果证明“当前求解失败”不能等同于“目标无解”；它不证明从现场当前构型存在满足所有碰撞约束的完整直线路径。

当前 Home 的正常直线分支不传固定 J2 参数，本次失败也不能直接归因于“锁住 J2”。主要问题是解锁后仍缺少构型管理与限位约束求解。

## 5. 左 J7：模型允许，实机没有到达

现场第 646–649 行：

```text
pos_l_err=34,33,-51,-41,3,-42,5633
左手实际 J7 ≈ −89.8°
```

误差定义为 `actual_count − commanded_count`，项目的诊断转换为一圈 `4 × 65536` 个计数，且左 J7 模型角与设备角方向相同、偏移为 0。因此：

```text
5633 × 360 / (4 × 65536) = 7.73575°
命令 J7 ≈ −89.8° − 7.73575° = −97.53575°
```

使用日志中前一阶段的角度重新规划，终点为 −97.5660°，与反推命令吻合。模型左 J7 下界为 −2.23 rad，约 −127.77°，所以软件当前允许该命令。

强证据指向“规划范围与设备实际可执行范围不一致”；停在约 −90° 是驱动下限的明显线索，但目前没有驱动限位读回、故障状态或外部接触记录，不能认定一定是固件裁剪。

设备 SDK 已提供 `get_Min_Position()` / `get_Max_Position()`。应以只读方式取得各轴限制，与设备角/模型角映射后求交，再形成统一有效运行范围。不能直接删除 URDF 限位，也不能未经核实把全机型左 J7 统一改成 −90°。

## 6. 失败传播漏洞与长等待

### 6.1 发送完成被当作运动成功

`src/motion/planning.cpp::arm_line_move()`：

```cpp
const int exec = execute_arm_trajectory(...);
if (exec == 0)
    record_arm_cartesian_arrival(...); // bool 返回值被忽略
return exec;
```

轨迹发送完、末端实际到位是两个不同事件。本次左 J7 未到位时，后一个检查已经失败，外层仍可能收到 0。

### 6.2 Home 阶段失败只做记账

`move_arms_retract_to()` 多处将阶段失败记为 `ok=false`，仅在硬件中止时立即退出；随后仍继续计算并执行 XY、Z、姿态阶段。起点和前置条件改变后，动作组合不再等价于原先规划。

修正方向应为前置阶段失败后保持当前状态并返回具体原因；如需恢复，明确生成一条恢复路径，不能自动继续原有后续阶段。正常工况提高成功率应通过规划质量改善实现。

### 6.3 20–30 s 不能全部算作逆解耗时

`record_arm_cartesian_arrival()` 的默认等待为 15 s，本次日志明确触发该超时。右臂最终转姿态的离线轨迹约 6.38 s，左臂升 Z 轨迹约 1.14 s，此外还有 XY 和其他阶段。它们足以使总节拍达到数十秒量级。

终端缺少各阶段时间戳，离线 FK 后端也不是 Linux 交付库，不能据本机运行毫秒数判断真机 SDK 性能。后续日志应分开记录 `planning_ms`、`execution_ms`、`settle_ms`、首个失败关节、命令/实际角和有效限位，而不是只打印一个 −4。

## 7. 标定图像与接近动作

两类故障应分开处理。

头相机终端证据显示四码识别及料盘解算成功，重投影约 0.66–0.67 px。标定图像通过 `head_image_path` 返回相对路径；Web 用自身的 `PROJECT_ROOT` 拼接，并要求文件位于自身 runtime 下的 `debug_picture/calibration` 中。两个进程 runtime 不同，就会读错目录。现场笔记给出的正确机器人 runtime 为 `session.6fYbjFFf/runtime`，但笔记本身不是文件存在性或 HTTP 请求成功的独立证明。

远程 `7213bea` 只新增问题记录，没有包含本地上一轮的 Web 自动发现 runtime 修改。本地 `run_web.sh` 与 `active_runtime.py` 改动仍未提交；不能认为机器人已经具备这项新行为。当前现场可按笔记中的实际 runtime 显式启动 Web，不需要重启机器人进程。

`runtime_context.sh` 还有一个可以独立确认的启动缺陷：`export T170_ROOT="$(cd ... && pwd)"` 中，`export` 的成功返回会掩盖命令替换里的 `cd` 失败。指定不存在的 runtime 时，根目录可能变为空，随后回退到源码目录并生成另一份会话。这与笔记描述的新建目录机制一致，已用不访问设备的 Bash 最小例子验证。启动脚本应先单独验证目录，再赋值并导出；仅增加默认自动发现还不能覆盖显式错误路径。

运动方面，`move_d` 先执行大段接近 `line(initial)`，成功后才执行 `local(d)` 并拍手相机图。此次右臂 `line_trajectory_fail ret=-4` 与“机械臂接近失败 code=-4”对应，说明失败在前一段轨迹规划，尚不能算手相机取图或 IBVS 问题。

具体失败关节仍需该次 `picture_debug/line_trajectory_fail.txt` 的目标和完整起点。当前上传记录没有这些数据，不将 J6 边界原因直接套用到该次标定失败。

## 8. 修改顺序

1. **统一真实约束和失败语义。** 设备限制只读取得并映射到模型角；各阶段使用统一有效限位。到位等待失败向上返回，Home 前置阶段失败立即结束当前动作链。补全阶段计时和失败数据。
2. **重新定义标准 Home。** 增加独立的、经过确认的左右臂 Home 模型关节构型。不要把 `retract_motion.ready_*` 当作 Home：它们是传送带准备构型。必要时先完成短距离脱离料盘，再以关节轨迹回 Home，检查路径上的手臂/工件扫掠；不强制整个返回过程保持 TCP 姿态或通过多个笛卡尔折点。
3. **改进任务直线求解。** 保留正确模型与 IO 转换，采用带关节边界的局部优化，加入偏好构型、关节居中/限位回避；连续轨迹沿用前一解。单点全局回退只生成候选，不直接接受第一个满足 FK 的任意构型。对真正必须固定姿态的接近/下降继续保持任务约束。
4. **完成界面运行目录对齐。** 将已有自动发现修改与机器人主程序配套部署，检查真实标定图像请求，再验证标定接近。

固定 J2 可作为某些解析方法或局部任务的冗余参数，但不应充当通用肘部策略。优先姿态、连续性、限位、碰撞几何需要在求解与规划中表达，不需要先引入强化学习。

参考实现：

- [Pink](https://github.com/pink-kinematics/pink)：加权任务、偏好姿态任务，以及配置/速度约束的二次规划。适合参考局部求解问题的表达方式，不等于仅增加一个 posture 权重就能保证所有路径可行。
- [TRAC-IK 官方项目](https://traclabs.com/projects/trac-ik/) 与 [MoveIt 官方集成说明](https://github.com/moveit/moveit2_tutorials/blob/main/doc/how_to_guides/trac_ik/trac_ik_tutorial.rst)：明确讨论关节限位引起的局部求解困难；提供基于种子距离或可操作度的解选择。参考求解策略不要求本项目迁移 ROS 2。

这些公开方案可以支撑技术选择，不能据此推断某家人形机器人企业未公开的内部实现。

## 9. 离线复现

本目录中的 `replay.cpp` 使用独立 MDH FK 后端调用当前实际的 `Arm` 适配器，不链接 Linux 算法 `.so`、设备库、CAN 或相机。原生单点逆解刻意返回不可用，因此这里只评估应用层局部算法。

参考配置来自本地此前生成的 No.124 3 kg 离线运行目录，不是机器人导出的配置快照。关节角仅有终端打印的一位小数，复现数值不能替代真机完整精度数据。`provenance.json` 记录源文件和配置摘要。

从仓库根目录运行，编译环境需要 C++20 与 yaml-cpp，Eigen 使用仓库内版本：

```bash
cmake -S docs/validation/home_failure_20261118 \
  -B /tmp/t170-home-failure-replay -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/t170-home-failure-replay --parallel 2
/tmp/t170-home-failure-replay/home_failure_replay \
  docs/validation/home_failure_20261118/reference_config/Robot_Model.yaml
```

前两项只检查第一次 Home 的单点数值求解，不将其误作现场使用的 TCP 直线。后六项重放对应直线；逐点诊断经欧拉角往返，可能存在浮点微差。替代种子的成功仅表示模型终点存在解，不表示候选构型适合上机。

上一轮中点 ±5 mm 和示教位附近的小范围测试没有覆盖本次实际任务姿态、近限位平移和 Home 构型一致性。测试通过只说明这些小范围用例通过，不足以证明 SDK 替换已达到实机运行要求。
